# 云文档协同（Co-scribe）

## 1. 概述

Co-scribe 让 agent 成为共享云文档里的一名协作者。你把文档共享给它的服务账号地址，在评论里 @ 它，它就在那条评论线程里给出修改提议。**在人回复批准词之前，正文不会有任何改动。**

整个循环留在文档里——不用把文字复制到聊天窗口、再把改好的粘回去。

```
你        @co-scribe 这句话优化一下
Agent     ⏳ 正在处理…
Agent     【拟议修改 1/1】 原文 → 拟改为，附理由
你        同意
Agent     已应用上述修改。            ← 正文在这一步才改，不是更早
```

本版本只支持 Google Docs。与平台相关的部分全部收在一个 provider 接口后面，因此接入第二个平台是去实现它，而不是重做整个循环。

**默认关闭。** `clouddoc.enabled` 为 `false` 时，后台服务不会被构造，Google 相关的库也不会被导入。

## 2. 快速开始

### 2.1 创建服务账号

agent 需要**属于它自己**的身份，而不是借用你的。Google Cloud 的服务账号提供了这一点：凭证留在你手里，而它在文档修订历史里的编辑与你的可以区分开。

1. 在 [Google Cloud 控制台](https://console.cloud.google.com/)创建（或选择）一个项目。
2. 为该项目启用 **Google Docs API** 与 **Google Drive API**。
3. 创建服务账号，然后为它创建一个 **JSON 密钥**并下载。
4. 记下服务账号的邮箱地址，形如 `name@project-id.iam.gserviceaccount.com`。这个地址就是 agent 在所有文档里的身份。

密钥文件请放在仓库之外。**拿到它的人就能以 agent 的身份行事。**

### 2.2 共享文档

像共享给同事一样，把文档共享给那个服务账号地址，并给**编辑者**权限。

**共享就是纳管。** 打开「文档」面板（或点刷新）时，Co-scribe 会把共享给该账号、且它确实能编辑的文档全部自动纳管——不必再回来粘一次链接。共享本身已经是一次明确的授权动作，再确认一遍只是仪式。这之所以不冒进，是因为**纳管只花轮询**：一篇被纳管的文档在有人把评论指派给 agent 之前，不会消耗任何轮次。

**仅给评论权不够，而且失败方式是静默的。** 没有编辑权时，Google 不再返回 revision id——并发保护正是靠它；同时权限列表开始返回 403——链接公开告警正是靠它。而评论仍然读得到，所以 agent 看起来一切正常、照常给出提议，却**永远无法应用**。Co-scribe 会拒绝纳管这样的文档并在启动时明确告知。

### 2.3 配置

```yaml
clouddoc:
  enabled: true
  connections:
    - credentials_file: /secure/path/to/service-account.json
      documents:
        - https://docs.google.com/document/d/<文档id>/edit    # 链接或裸 id 均可
```

一个连接 = 一个服务账号。要让多个身份各自纳管不同文档，就加多个连接——**同一篇文档只能属于一个连接**，重复的会在启动时被跳过并告警（两个身份盯同一篇，每条 @ 会收到两份回应）。

> 早先的写法（顶层 `credentials_file` 与 `documents`）仍然可用，等同于只有一个连接；从界面上做任何增删后会自动升级成上面的形状。

重启 gateway。启动日志会确认 watcher 已运行：

```
[App] clouddoc watcher started for 1 document(s)
```

配置里只有 `credentials_file` 是必填的：**文档可以在界面里加**，见下节。

### 2.4 在界面里管理文档

侧栏的**文档**面板是日常入口。左边是连接（厂商 × 服务账号），右边是该连接纳管的文档。

- **共享地址**在右侧标题栏，鼠标移上去出现「复制」——粘进 Google 文档的「共享」对话框即可，不必去 JSON 密钥里找。
- **自动纳管**：打开面板或点刷新时，共享给该账号且可编辑的文档会自动出现在列表里。只给了评论权的会单独列出并说明改法——那是最常见的一步之差，藏起来只会让人以为共享没生效。
- **手动添加**：不想等、或文档不在自动列表里（比如 Drive API 还没开），把链接粘进底部输入框。**粘贴即校验**：权限没问题就直接纳管；只有评论权会当场告诉你要改成「编辑者」；还没共享给该地址会提示先去共享。
- **每篇文档的状态**：正常 / 仅评论权 / 已冻结，鼠标移上去有说明。标题栏的三个小灯是分类计数。
- **刷新**：逐篇重新检查权限。**权限修好之后点它就能恢复**——连续失败被暂停轮询的文档也一样。
- **点文档卡片**在 Google 文档里打开它（用你自己的账号，不是 agent 的）。

界面的增删会写回 `config.yaml` 并**立即生效**，不需要重启。

### 2.5 使用

选中一段文字，添加评论，输入 `@` 后跟服务账号地址——文档共享给它之后，Google 的自动补全会把它列出来。**然后勾上「指派给」**。

**只有指派才会触发。** 单纯 @ 一下是**标记**，不是派活：

| 你做的 | 含义 | 结果 |
|---|---|---|
| `@` 它 | 标记：这条与它有关 | 不触发。它会回一句提示，告诉你指派或去对话里批量处理 |
| `@` 它 **并指派给它** | 派活：这是它的任务 | 触发。占位 → 提议 → 你批准 → 落地 |
| 「标记为完成」 | 收工 | 出队，不再触发 |

这样区分有两个实在的理由。其一，**指派点名一个账号**，所以一篇文档里可以有好几个 agent，各做各的、互不打扰；而 @ 谁都能 @ 谁，它不该等于把活交出去。其二，一条评论是不是任务，从此在文档界面上**看得见**——指派的评论显示为待办，谁负责一目了然。

然后在线程里回复：

| 回复 | 效果 |
|---|---|
| `同意` / `approve` | 提议被应用到正文 |
| `原文` / `keep` | 提议作废，文字保持不变 |
| 其他任何内容 | 视为新意见，agent 据此修订后重新提议 |

**语言**：评论用中文或英文都行，agent 用**同一种语言**回你。但提议末尾要你照打的那两个词——`approve` / `keep`——**始终是英文**，因为它们是命令而不是措辞；打「同意」「原文」同样生效（判定收双语词表），只是提示里只给一种写法，省得猜。判定是归一化后**精确匹配**。`同意实施`、`同意，但第二句再改改` 都算新意见而不是批准——这是刻意的，失败方向朝「多问一轮」而不是「应用了你没打算要的东西」。

## 3. 使用建议

**开一个话头：顶层评论 @ 它并指派给它。**

**同一条线程里接着说，不用再指派。** 线程只要还指派着它、还没标记完成，你在里面的每一条新回复它都会看到并回应。反过来，指派一撤或标记完成，这条线程就静默了。

**它不会被另一个 agent 的发言叫醒。** 服务账号写的任何东西都不构成触发——包括它自己的和别人 agent 的。否则两个 agent 在同一条线程里会一直互相回应下去，每一轮又产生触发下一轮的那条回复。

**原文改了，针对它的评论与提议就失效了。** 你或别人（或它自己在对话里）改动了某段文字之后，锚定在那段文字上的评论无法再定位，悬置的提议也不再适用——它会明说，请你对当前文字重新评论。这是刻意的：文字都不在了，针对旧文字的修改不该继续生效。

**选中你想改的那段。** 选区不只是上下文，它是**边界**：被批准的提议只能改动引用范围加上两侧的少量余量。这就是为什么「有人对一句话评论了」不会变成「agent 重写了整节」。

**全文级的工作在对话里做，但有边界。** 评论里的作业范围限于选区；要整体改写，去 Jiuwen 对话里说（见第 8 节）。**从空文档生成内容**也在对话里做，而且只产出纯文本——标题样式、加粗需要你自己在文档里设置。

**改不了格式。** agent 处理的是纯文本，加粗、斜体、标题、颜色都无法从评论里修改。请只提措辞层面的要求，格式自己设置。

**共享给谁，谁就能驱动它。** Google 的评论权限不携带可靠的作者身份，因此 Co-scribe **无法**限制谁可以触发 agent、谁可以批准它的提议——任何有评论权的人两件事都能做。请把共享名单直接当作授权名单。如果文档是「知道链接的任何人」，那就等于开放给所有持链接的人，Co-scribe 会在启动时对这种共享态告警。

## 4. 配置

### 4.1 `config.yaml`

```yaml
clouddoc:
  enabled: false
  connections:
    - credentials_file: ""        # 服务账号 JSON 密钥路径
      documents: []               # 链接或裸文档 id

  # 以下各项为所有连接共用
  poll_interval_seconds: 30       # Drive 没有评论的推送通道，只能轮询
  turn_timeout_seconds: 540       # 启动时会被钳到传输层上限之下
  session_max_turns: 50           # 单文档会话跑满这么多轮后轮换

  conventions_marker: "co-scribe 约定"

  approve_word: ["同意", "approve"]   # 词表：回复须精确等于其中某一项
  keep_word: ["原文", "keep"]

  rail:
    adjacent_budget: 200          # 改动可以超出引用范围多远
    max_quote_chars: 400
    max_insert_chars: 2000
    max_edits: 10
```

全部可配置串——约定标记，以及两个词表里的**每一项**——两两不得相等、不得互为前缀，同一个词表内部也算。这一条在启动时校验，不通过就拒绝启动：两个词表之间相撞，同一句回复会既是「应用」又是「保留」。

> 早先版本有一个 `trigger_word`（默认 `co-scribe:`），以文本开头即可触发。它已被移除：那个词**不带身份**，一条以它开头的评论会触发**所有**盯着这篇文档的部署，而这在多人各带 agent 的共享文档里是常态。

### 4.2 权限

如果你的部署设了 `permissions.enabled: true`，无人值守路径用到的四个工具必须是 `allow`：

```yaml
permissions:
  tools:
    clouddoc_read: allow
    clouddoc_list_comments: allow
    clouddoc_propose_edit: allow
    clouddoc_reply_comment: allow
```

无人值守的轮次没有人可以回答确认，因此 `ask` 会被判成**拒绝**而不是弹出询问。把其中任何一个设成 `ask`，功能会静默失效。

还有两个只在对话路径注册、无人值守路径**根本不注册**的工具，所以它们的设置只作用于对话场景：

* `clouddoc_batch_edit`（直接改正文）默认 `ask`。
* `clouddoc_list_documents`（列出本连接纳管的文档）默认 `allow`。对话路径拿不到 doc_id，
  没有它，agent 只能反过来问用户要链接——哪怕面板上正列着那篇文档。它不进无人值守白名单：
  评论触发的轮次只被授权处理触发它的那一篇，给全量清单等于扩大可见范围。

**纳管多篇时，选哪一篇是代码轨，不是提示词。** 当前连接纳管两篇及以上，而用户的话里没有
出现目标文档的标题、链接或 id 时，所有针对文档的操作（读、列评论、改正文、发提议、回评论）
一律拒绝，并要求先问用户。证据只认**用户自己输入的文本**——模型选了哪个 doc_id 不算数，
拿它当证据是循环论证；`ask_user` 的答复算数，这正是被拒绝的轮次能自救的路径。
无人值守轮次豁免：那里的文档由网关绑定，本就不是模型选的。

`clouddoc_list_documents` 会把用户在本次会话里已指明的那一篇标为 `user_named=true`，
让模型在**挑之前**就知道，而不是挑错后被拒绝再改。

> 早先版本还有 `clouddoc_edit` 与 `clouddoc_resolve_comment`。前者被 `clouddoc_batch_edit` 取代——多处改动一次原子提交，一次确认。后者被移除：**结帖是评论者的验收动作**，由 agent 代做等于替别人宣布接受，而共享服务账号的身份模型无法判断驱动者是否有这个资格。

## 5. 文档约定

协作者可以留一条以约定标记开头的顶层评论，为这篇文档设定写作约定：

```
co-scribe 约定
句子尽量短。
产品名首次出现时用全称。
```

这些约定**只约束风格**。其中任何试图改变 agent 工作方式的内容——它能改什么、能用哪些工具、谁的批准算数——一律忽略。回复永远不算约定，所以仅有评论权的人无法借此注入策略。有多条时以**最早**的一条为准。

agent 自身的应答策略在本版本里是**固定的**，不可配置；文档约定只能影响写作风格。

## 6. 限制

- **锚定精度**：Google 的评论 API 返回引用文本但不返回索引。当这段文字在文档里出现多次时，agent 无法判断你指的是哪一处，会请你重新评论。
- **延迟**：30 秒轮询意味着平均约 15 秒的触发延迟。
- **配额**：所有纳管文档共享服务账号的配额。文档之间**并发**轮询，所以某一篇的慢轮次不会拖慢其他篇。
- **单实例**：watcher 假定只有一个 gateway 实例。两个实例共用同一份状态文件会各自派发同一个触发。
- **成本**：每次触发就是一轮 agent 作业。纳管大量活跃文档的部署应当据此评估模型预算。
- **企业策略**：部分 Google Workspace 租户禁止把域外服务账号加为协作者。变通办法是由贵方管理员创建一个域内服务账号。

## 7. 排查

| 现象 | 原因 |
|---|---|
| @ 了之后没有任何反应 | **只 @ 不会触发，要指派**——它会在评论下回一句提示告诉你这件事；如果连那句提示都没有，那就是文档没被纳管（看「文档」面板，或配置里的 `connections[].documents`），或手改了配置却没重启 gateway（从面板改的不用重启） |
| 指派了仍然没反应 | 这条评论是不是已经「标记为完成」了？完成即出队。也可能指派给了**另一个** agent 的地址 |
| 启动日志说功能未启动 | 凭证读不到、文档 id 解析失败、或两个可配置串相撞——日志会指明是哪一项 |
| 提议出来了但回复批准没反应 | 检查回复是否**恰好**是某个批准词。`同意实施` 属于新意见，不是批准 |
| 想加 `ok`/`好` 这类词做批准词 | 不建议：它们是日常应答，有人只想说「我看到了」，文档就被改了。批准词应当只包含明确表达承诺的词 |
| “the quoted range can no longer be located uniquely…” | 自评论写下以来，引用的文字被改过、或在文档里出现了多次。请对当前文字重新评论 |
| 修好权限（或恢复共享）后文档仍无反应 | 连续失败的文档会停止轮询。在「文档」面板点**刷新**——它逐篇重新检查，通过的当场解冻。没有界面时，重启 gateway 每次启动也会做一次同样的检查 |
| 「这条提议未通过范围检查」 | 提议超出了引用范围，或试图往纯文本正文里写入格式记号 |

## 8. 在对话里操作文档

文档里的 @+指派是一条路径；Jiuwen 对话里直接操作是另一条。两条作用于同一份文档，分工是**指派的归文档侧，其余归对话侧**。

对话里可以：

- **读文档、列评论**——包括那些只 @ 了 agent、还没指派的
- **回复评论**（已解决的除外）
- **直接改正文**：多处改动一次原子提交
- **往空文档写入首版内容**

对话里**不能**：

- **结帖**。这是评论者的验收动作
- **动已指派的任务**。那是文档侧的活，agent 会跳过
- **写 markdown**。正文是纯文本，`##`、`- `、`**加粗**` 会原样出现在文档里。章节标题请写成单独一行普通文字，样式你自己套

### 与文档侧的两条边界

**有已指派未完成的任务时，对话里不改正文。** 不是因为怕锚定失效（那已定义为失效），而是两个写入者同时动手会做无用功。先处理完或标记完成，再让它改。

**整篇改写会让既有评论失效。** 引用文本找不到了，那些线程之后无法再触发——它们仍然可读，但要 agent 处理得对当前文字重新评论。

### 安全等级不一样，这是有意的

| | 文档侧（指派触发） | 对话侧 |
|---|---|---|
| 工具 | 闭集四个 | 五个 |
| 范围边界 | 强制：选区即边界 | **无**——由你在场把关 |
| 改动方式 | 提议 → 你批准 → 系统落地 | 直接改，`ask` 确认 |
| 记号防护 | 范围轨拒绝新增记号 | 批量工具拒绝结构性记号 |

文档侧没有人在场，所以保证必须写在代码里；对话侧你在场，保证来自你。**别把文档侧「选区即边界」的心理预期带到对话里**——那里没有选区。
