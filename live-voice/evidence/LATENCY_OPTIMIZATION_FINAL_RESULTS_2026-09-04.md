## 4. 缺陷 A 的机制（已复现、已修复）

journal 里失败轮的 effect 行停在 `prepared`、`recovery_json` 为空、语义绑定已写入。用真实 journal 的 registry 夹具复现：解析器宣告 dialogue 后**立即返回**（决策先于投机任务运行），提交确定性地以同一错误失败。链条：门已 `release` → `hold_presentation` 拒绝"已结算的门" → `before_dispatch` 在写 checkpoint 之前失败 → 派发回滚 → 外层 `_run_unified_foreground_effect` 的幂等提升兜底发现 recovery 为空而抛 MISSING，**把真实错误掩盖成了 owner 丢失**。生产里宣告与决策完成只差 ~150ms（§5），这个窗口每几轮就会撞上一次。

修复：已 `release` 的门不装暂扣（此时没有任何东西是临时的）；已 `discard`/失败/取消的门拒绝派发，客户端看到的是语义错误本身。两条复现用例修复前失败、修复后通过。

顺带发现（未改）：`_run_unified_foreground_effect` 的外层提升兜底会把"派发前失败"统一掩盖为 MISSING；建议在兜底前区分 checkpoint 是否已写。

## 5. 结构化并行到底并行了多少

从 swarm 日志按 submit 窗口解析：语义调用（现为流式）在 submit 后 +155ms 启动；Agent 流式调用在语义调用启动后 **+1,375ms（p50，n=16）** 启动；而语义调用整体 p50 ≈ 1,516ms（切分）。即 `route` 字段出现在语义调用开始后约 1.4s——**DeepSeek 的首 token 时延是流式语义调用的地板**，宣告只比决策完成早 ~150ms，short 档 `submit→首 delta` 782→766 几乎不变；本批收益主要来自 submit 往返本身缩短（2,016→1,722）。

要吃到完整的 ~1.5s，只有两条路（暂扣门已经为此准备好了）：
1. **t=0 起并行**：submit 一到就派发 Agent（对话为默认假设），语义决策只做验证；task 路由（约 1/5 回合）会浪费一次被丢弃的 Agent 调用。
2. **前置门**：任务存储无任务且无待决上下文时，对话是唯一可能路由，跳过语义模型。
