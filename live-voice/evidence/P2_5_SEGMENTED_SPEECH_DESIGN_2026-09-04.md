# P2-5 稳定内容逐段放行 + 未提交后缀修订：设计边界与用例 — 2026-09-04

> 依据用户 2026-09-04 的决定：选方案 1 的修正版——先放行满足播报条件的稳定内容，修订只处理尚未提交播放的后缀；需要事实核对的结论不能先说再核对；不做"先播草稿再补救"。
> 四条边界原文：①先区分整理与核对；②修订只能替换可撤销的后缀；③历史记录保持真实；④失败和打断不能放出草稿。
> 本文把边界落到现有管线的具体接口上，并列出每条边界对应的用例。实现前需要用户确认 §5 的两处范围决定。

## 1. 现有管线的事实（本分支 `2aef1f533` + t=0）

- **单元**：Runtime 把每个可用 `chat.final` 变成一个文本呈现单元 `agent-final:<rid>:<seq>`（`produce_unit` + `enqueue_unit`），`chat.delta` 只是通知，不是单元；第二个可用 final 报 `DUPLICATE_AGENT_FINAL`。
- **呈现与历史**：文本单元只有 UI ACK 后才算"已呈现"，音频只有播放 ACK 后才算；history 写入是**每个单元 ACK 后各追加一条**（键含 `contiguous_cursor:seq:digest`，幂等）。不存在"全文覆盖"的写法；未 ACK 的单元不进 history。
- **修订**：`finalize_spoken_answer` 在适配器正式流的 `chat.final` 上串行等待；它混合两种职责——长度整理（>200 字，无 thinking，6s）与算术复核（有工具结果且含时间/费用量，thinking，12s）。复核是模型提示 + 结构检查，不是确定性校验器。
- **final 语义**：正常回合 `chat.final` 重发整篇；被截断的回合只带尾巴。
- **前端**：按单元 `playAgentText(unit_id)`，播放队列按 `unit_id+seq` 续接（`nextStartTime`），有整响应 `stopPlayout`，没有按单元失效；未发现只认 `agent-final` 的过滤。
- **实习生可复用件**：`stable_sentence_policy.py`（观察→候选→提交→final 对账，处置 `EXACT_PREFIX / REWRITE_BEFORE_COMMIT / REWRITE_AFTER_COMMIT / EXACT_REPLAY`）、`authoritative_final_chunking.py`（尾巴分块，≤4 块）、`c019_lifecycle_model.py`（行为规格）；不复用网关 PARK/PROMOTE 传输与能力协商。

## 2. 目标状态模型

一个响应的文本是有序段的序列，每段处于：`draft → stable → cleared → released → presented`。

- **stable**：按句边界与稳定前缀策略确定的、不会被后续 delta 改写的前缀增量（要求 Agent delta 为 append-only；非 append-only 时整轮退回单单元）。
- **cleared**：整理与核对完成。纯表达整理逐段做（确定性清理：去 markdown/控制标记/列表符号，不调模型）；需要核对的段，在核对完成前不得 released。
- **released**：成为呈现单元并入队，**从此不可变**。
- **presented**：ACK 后计入 history。

修订只能作用于 `draft/stable` 尚未 released 的后缀；released 段永不改写；若 final 与已放行前缀矛盾（对账非 `EXACT_PREFIX`），不改写、不重念，走 §3.3 的更正路径。

## 3. 边界落点

### 3.1 整理与核对分离（边界①）

| 内容 | 处理 | 何时 |
|---|---|---|
| 无工具结果回合的段 | 确定性清理后放行 | 段稳定即放行 |
| 有工具结果回合 | 与今天相同：final 后整篇复核（算术路径）再播；**不逐段放行** | final 后 |
| 跨句依赖 | 稳定前缀策略以句为单位，但工具结果回合整篇等待，天然覆盖"结论、条件、限制一起处理" | — |

理由：现有代码里唯一存在的事实核对触发条件就是"有工具结果"。无工具回合的事实来自模型知识，今天也没有核对，逐段放行不会降低它的正确性；而工具回合正是"先说再核对"的风险所在，所以首批把它整轮排除在流式之外。这样"这班高铁来得及"这种结论只会出现在工具回合，仍然在复核之后才播。

### 3.2 后缀替换（边界②）

首批不存在"已入客户端队列的旧后缀被替换"的情形：released 段不可变，未 released 的后缀客户端还没收到。final 到达时，Runtime 用前缀匹配切出尾巴（`final.startswith(released_prefix)`），只对尾巴做清理并作为最后一个单元放行。若 final 不以已放行前缀开头（对账失败）：不重念已放行内容，尾巴不播，文本通道显示 final 全文，记录 `segment_reconciliation_mismatch`，并进入 §3.3。因此客户端不需要新的"按单元失效"能力；打断沿用现有整响应 `stopPlayout`。

### 3.3 历史真实（边界③）

- history 已经是按单元 ACK 追加，已播段以其播出时的文本入史；未播的尾巴不入史。
- 对账失败或后来发现前文错误：不改写已入史内容，追加一个**更正单元**（以"更正：…"开头的短句，由 final 中与前缀矛盾的部分生成；首批为固定模板 + 差异句），同样经 ACK 入史。文本面板保持"已播内容 + 更正"，不用 final 全文替换。

### 3.4 失败与打断（边界④）

- 尾巴整理失败（超时/异常）：已放行段保留；尾巴改念一个固定的如实说明单元（"后面的内容我没能整理好，请看文字。"），不念草稿全文。
- 打断（barge-in）：现有 `interrupt_generation` 围栏使响应 superseded，之后到达的段/final/更正一律被围栏丢弃；正式流被取消，不再产生新段；已入队音频由现有 `stopPlayout` 停止；迟到的 TTS 不得恢复播放，也不触发额外 Agent/Task 动作（复用 t=0 的丢弃语义与测试方法）。

## 4. 用例（每条边界至少一条能杀死反向变异体的用例）

1. 段放行顺序与不可变：三个稳定段依次成为单元，seq 递增，内容与 delta 一致；final 到达后只追加尾巴单元，已放行单元内容与 ID 不变。（变异：final 覆盖已放行内容 → 红）
2. 对账失败不重念：final 不以前缀开头 → 无尾巴单元、无重念、追加更正单元、记录 mismatch。（变异：直接播 final → 红）
3. 工具结果回合不逐段放行：捕获到工具结果的回合，delta 不产生段，final 走整篇复核后单单元。（变异：工具回合也放行 → 红）
4. 中途出现工具结果：之前已放行的段保留不变，之后的内容等待 final 复核。（变异：撤回已放行段 → 红）
5. 确定性清理不调模型：段放行路径零 `llm_call`；清理去掉 markdown/控制标记。（变异：清理调用模型 → 红）
6. 尾巴整理失败：已放行段保留，追加固定说明单元，不播草稿尾巴。（变异：播草稿 → 红）
7. 打断：superseded 之后到达的段/final/更正被丢弃，零新单元、零 Agent/Task 动作、`stopPlayout` 被调用。（变异：迟到段仍入队 → 红）
8. history：多单元各自 ACK 后各追加一条，顺序与 seq 一致，未 ACK 的尾巴不入史；更正单元入史。（变异：按响应合并覆盖 → 红）
9. 非 append-only 流：检测到 delta 非追加 → 整轮退回单单元，不放行任何段。（变异：仍放行 → 红）
10. 与 t=0 候选接入的组合：候选缓冲中的 delta 在接入后同样按段放行，暂扣期间零单元。

## 5. 需要用户确认的两处范围决定

1. **工具结果回合整轮不流式**（§3.1）。代价：tool 档不从 P2-5 受益（它今天 final 只比首 delta 晚 ~1s，收益本来就小）；收益：不存在未经复核先播的事实。
2. **无工具回合的长度整理改为确定性清理 + 提示约束**。代价：长答按草稿原句播出，可能比今天经模型压缩后的口播更长（今天 long 235→157 字）；收益：首音提前，且不会出现"念一句改一句"。答案长度作为 A/B 的必测指标；若明显变长，再评估逐段模型整理。

## 6. A/B 指标（按用户清单）

- 首个**有效**答案的可听时延 p50/p95：以首个非填充语单元（过滤"好的/我看看/让我想想"类开头）的下行首帧计，另报首帧。
- 事实错误、前后矛盾、事后更正次数：自动报 mismatch/更正单元计数；答案文本随 rounds 记录供人工抽检。
- 句间停顿、重复/漏播、打断后残余音频：驱动器按单元记录下行帧时间，报单元间隙 p95；拼接单元文本与 final 比对；新增 barge 场景测打断后残余帧数。
- 修订/整理失败率与额外模型调用：日志计数。
- 答案字数、单元数。

"2~3 秒"只是待验证假设：收益 = 首个有效段就绪时刻与 final 的距离，long 档 `submit→final` 3.5s 而首 delta 0.14s，理论上限约 3s，实际取决于首句长度与清理。

## 7. 实施顺序

- A：段放行（适配器 `chat.segment` 事件 + Runtime 段单元 + final 尾巴切分 + 对账）、工具回合排除、打断/失败语义、用例 1–10、同基线 A/B（开关 `LIVE_VOICE_SEGMENTED_SPEECH`）。
- B：更正单元的生成策略与文案；barge 场景进驱动器。
- C：若答案变长明显，评估逐段模型整理（仍不触碰已放行段）。
