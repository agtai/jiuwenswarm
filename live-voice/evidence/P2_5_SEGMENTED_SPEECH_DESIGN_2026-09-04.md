# P2-5 稳定内容逐段放行：准入核实、量化与可行范围（v2）— 2026-09-04

> v1 按用户四条边界（①整理与核对分离；②修订只替换可撤销后缀；③历史真实；④失败与打断不放出草稿）写了落点与用例。
> 用户随后指出 v1 的两处范围决定不能按原文批准：决定 1 的准入方式有漏洞（"目前没有工具结果"≠"这条路径不会再调工具"），决定 2 是产品行为取舍而非必然推论，且收益数字口径有误。
> v2 把这些逐条对到代码与逐请求数据上。结论先行：**按"首段放行前须有可信执行状态保证不再调工具"的准入规则，现框架下对草稿生成的逐句放行覆盖为零**；可准入的剩余收益只有修订输出的逐句放行（≤0.9s，仅 medium/long），以及两处修复。v1 的决定 2 撤回。

## 0. 结论

| 项 | v1 说法 | 核实结果 |
|---|---|---|
| 准入 | 未捕获到工具结果的回合逐段放行 | 控制器把每个 content 块立即流出，同一条消息末尾才知道有没有 tool_calls；final 只在"没有新任务"时判定；没有独立的最终回答阶段。唯一可信的"不可能调工具"状态是 rail 的无工具会话（模型输入 `tools=[]`），而对话回合 `allow_tools` 恒为 True。**草稿逐句放行可准入覆盖 = 0** |
| "工具回合原样不动" | 与今天相同 | 不准确。当前"长度优先于算术"的顺序是 P0-1 引入的回归：>200 字且含时间/费用量的工具回答只做长度整理、不做算术复核。基线是"≤200 且无工具结果才跳过，否则一律 thinking 修订"。应修为算术优先 |
| 决定 2（去模型整理） | 草稿已在 200 字附近 | 错。修订前草稿 medium 277–351、long 513–597 字；修订后口播 76–174 字。按 4 字/秒估算，去整理会让 medium 多播约 50 秒、long 约 100 秒（未实测音频）。**撤回** |
| 收益估算 | tool 上限 ≈1s；提前 2–3s | 逐请求：tool `首 delta→final` p50 1,480 [340–1,787]（n=4，final 为修订后）；medium 3,050 / long 4,072，其中修订 1,160 / 1,357，其余 1.9 / 2.7s 是生成时间——这部分正是不可准入的 |
| TTS 句级切分 | 未评估 | 无收益：final→TTS 首块 0.6–0.7s，与字数无关（41 字 664ms，149 字 608ms） |

## 1. 准入：框架事实（本分支 `2aef1f533` + t=0，openjiuwen 已安装版本）

- **content 先于 tool_calls 流出**：`openjiuwen/core/application/llm_agent/llm_controller.py` 769–792——每个 `chunk.content` 立即作为 `llm_output` 写入流；`tool_calls` 在同一条消息内累计，消息结束后才组成 `AssistantMessage(tool_calls=...)`。所以"首个稳定句已到、尚未见到工具事件"不能推出"本消息没有工具调用"。用户举的"先说赶得上、再读文件、最后改口"在协议层是可能的。
- **final 的判定时机**：`_handle_task_completed` 340–344——`_generate_next_plan` 返回无新任务时才发 final；有 tool_calls 就继续迭代。**没有强制无工具的收尾阶段**；唯一例外是超过 `max_iteration` 时发固定文本"Maximum iteration reached"。
- **唯一可信的无工具状态**：`stream_event_rail.py` 867–871——无工具会话在 `before_model_call` 把 `ctx.inputs.tools = []`（模型拿不到工具 schema），947 行执行侧再兜 `FORMAL_TOOL_EXECUTION_FORBIDDEN`。这是"输出路径不可能调工具"的执行状态。
- **对话回合从不无工具**：`product_composition_registry.py` 8275——`allow_tools = decision.route == "dialogue" and continuation_action != "decline"`；task/clarify 不进 Agent，decline 直接呈现。生产中没有任何 Agent 回合以无工具方式执行。
- **无工具回合今天整篇缓冲**：`jiuwenswarm_round_harness.py` 804–870——`allow_tools=False` 时所有 `chat.delta` 缓冲到 final（上限 32KB），并做控制标记检查后一次放出。若将来存在无工具回合，逐句放行要改这里，而不是适配器。
- **thinking 不会混入答案**：控制器把 `reasoning_content` 作为 `llm_reasoning` 单独流出，适配器映射为 `chat.reasoning`，Runtime 只把 `chat.final` 做成单元。
- **任务真相无事后校验**：w3 `bfef2b3ad` 把 Task 快照作为上下文条目 `live_voice.task_truth` 注入并在提示里约束，没有输出侧校验。"无工具≠无事实"成立：这些约束今天也只靠提示，流式不改变它，但也不能宣称"不碰事实"。

推论：要让草稿生成逐句放行满足准入，只能由产品定义"哪些对话回合以无工具方式派发"（模型输入 `tools=[]`）。用语义决策判"是否需要工具"不是可信执行状态，且等于为流式资格关闭本来需要的工具，与用户的约束相悖。**建议不定义这类回合，P2-5 的草稿流式搁置。**

- 20 次修订全部 `detailed_requested=false`。而 medium 的原话是"请用大约二百五十字介绍…"，long 是"请详细介绍…分成五个阶段"——两档都明确要求篇幅/细节，修订仍压到 200 字内。这是产品问题：提示里的"用户明确要求详细则例外"没有生效。

## 3. 可准入的剩余范围

### 3.1 修订输出逐句放行（B'）

修订调用 `finalize_spoken_answer` 以 `tools=[]` 调 `model.invoke`，今天是非流式、等整段 JSON。这条调用**在构造上不可能调工具**，满足准入；它的输入是已完成的草稿与工具结果，事实边界不变。改为流式并按句放行 `text` 字段：

- 收益上限 = 修订时长 −（首 token + 首句）：medium/long 约 0.5–0.9s；short/tool 无修订，无收益。
- 首批只做长度路径（无 thinking）。算术路径保持整段（thinking 后一次给出，避免"先陈述后复核"）。
- 已放行句不可变；流末 JSON 校验失败或超时：保留已放行部分 + 固定说明单元，不回退到草稿全文（顺带解决超时降级问题）；未放行任何句时念确定性 ≤200 字的句边界开头。
- 打断：沿用 t=0 的丢弃语义（迟到的句/final/更正一律不入队、零 Agent/Task 动作）。

### 3.2 修订顺序修复（C）

`spoken_revision_reason`：先判 `tool_results and _ARITHMETIC_QUANTITY` → arithmetic，再判长度。代价：>200 字且含量的工具回答回到 thinking 路径（12s 预算）。这是 P0-1 引入的回归，应独立修。

### 3.3 产品问题（不在本项内，记录）

修订对"用户明确要求篇幅/详细"的回合仍压缩到 200 字。是否放开是产品决定；放开会直接增加播报时长。

## 4. A/B 设计（用户提议的三组，按核实结果调整）

| 组 | 内容 | 目的 |
|---|---|---|
| A | 当前路径 | 基线 |
| B | 无工具结果回合取消长度修订，仍等 final | 单独量化取消重写的时延与播报时长影响（也回答 §3.3） |
| C' | A + 修订流式逐句（§3.1） | 单独量化可准入的流水线收益 |

共同指标：首个有效答案可听时延（过滤"好的/让我看看"类填充语单元，另报首帧）；播报总时长（驱动器排空下行，帧数×20ms）；完整回答耗时；事实错误/前后矛盾/事后更正（自动计 mismatch 与更正单元，文本随轮记录供抽检）；重复/漏播（单元拼接对比 final）；打断后残余帧（新增 barge 场景）；修订失败率与额外模型调用。

场景补充：medium/long 都明确要求篇幅或细节，需加一档无篇幅要求的知识问答（如"机器学习是什么？"），否则 B 组的播报时长被场景本身放大。
